# 第 9 阶段整体验收与发布准备

验收日期为 2026 年 11 月 28 日。候选版本位于 `codex/stage-9-admin`。本次使用本机 PostgreSQL 17.12、模拟 Supabase Auth、模拟模型上游与合成账号。上线需要另行确认。8.3 正式付费试点继续暂停。

## 运营到钱包的实测结果

系统管理员签发 3.00 美元兑换码。普通用户从登录入口进入、兑换、创建 API 密钥，再各发一笔非流式和流式请求。审计员按兑换码 ID 找到核销审计，收据编号与钱包入账记录相同。

| 同一普通账号 | 预占（美元） | 实扣（美元） | 释放（美元） | 钱包变动（美元） |
| --- | ---: | ---: | ---: | ---: |
| 兑换入账 | — | — | — | +3.00 |
| 非流式模拟调用 | 2.00 | 0.75 | 1.25 | -0.75 |
| 流式模拟调用 | 2.00 | 0.75 | 1.25 | -0.75 |

最终余额为 1.50 美元，预占归零。两笔使用记录均已结算，各自按请求编号匹配唯一扣费流水。普通用户会话和其有效 API 密钥均被后台拒绝，用户密钥列表、钱包流水及核销审计未返回测试密钥或兑换码明文。

最终应用构建及 68 项回归测试通过。原生 PostgreSQL 的 9 项专项覆盖渠道启停、轮换、回退、模型调价、在途扣费、用户停用与恢复、邀请、日志权限和系统设置。全量回归另覆盖删除账号、撤权、兑换并发、真实响应格式的离线模拟以及既有 Stripe 沙盒业务逻辑。完整合成请求编号和数据库快照保留在本机。

## 备份、恢复和应用回退

1. 在有上述业务数据的源库执行一次加密备份，并独立验证归档。迁移版本为 001–015，范围共 32 张表，账务一致性检查返回 0 项差异。
2. 另建空库，安装同版本数据库结构与相同的身份表结构，跳过种子数据。执行恢复时逐表比对行数和内容指纹，设置历史、角色、登录与操作日志、钱包、扣费和使用记录全部匹配。
3. 在副本复查运行角色权限。设置从版本 2 回退到版本 1 的值，生成版本 3。再回退到版本 0 的值，生成版本 4。审计记录对应版本 3 → 4，余额保持 1.50 美元。源库保持版本 2。
4. 在恢复副本启动上一版后台，数据库保持迁移 015。合成账号经登录入口验证成功，钱包和两笔用量可读，普通账号无后台权限。将旧应用环境中的单码额度设为 100 美元，数据库当前额度为 2 美元，签发 4 美元仍返回超限。回退目标已验证到该提交。[已验证的上一版后台](https://github.com/316878750/opentoken/commit/322f0e28deb253a3a0e53e65982b75584611029f)

## 正式发布顺序

1. 记录试点当前应用提交、数据库迁移版本、启用的模型与分组、已发布费率，以及有效运营签发上限。核对管理员首开账号、允许的渠道目的地和受控密钥引用。向正式试点发布前确认时间窗口与经办人。
2. 用迁移角色执行一次 `pnpm db:backup create`，再用 `pnpm db:backup verify <归档>` 检查表清单、可读性和账务差异。备份密钥单独保管。出现账务差异先查账。此前取消的每日备份及 15 分钟探针继续停用。[备份与恢复操作](backup.md)
3. 执行 `pnpm db:migrate`，用运行角色执行 `pnpm db:check`。逐项比对现有模型、费率及路由，再安排数据库接管。每个模型与分组先验证渠道、流式能力和计费证据。已有账号、钱包和数据不需重新播种。[渠道与模型迁移](stage9.md#93-渠道与模型绑定)
4. 发布经确认的应用提交。检查 `/api/health`、普通用户登录、管理员入口、运营只读设置、审计员日志及普通用户的拒绝访问。在正式开出首张兑换码或调用付费上游前，确认金额、账号和调用授权。
5. 出现异常时先暂停对应模块的新变更，保留在途请求结算。设置或渠道问题使用版本回退，再核对账本、费率与请求快照。应用回退使用本次核验且包含后台鉴权、账号停用和删除校验的版本。数据事故优先恢复到独立库比对，并核对备份后新增的请求、付款和流水，再决定切换。

恢复副本随后使用本阶段候选应用重新启动。健康接口、合成用户登录、余额、两笔使用记录、运营当前设置与单码额度再次核对通过。本次验收使用一次性本机备份。正式环境的发布、当次备份和发布后冒烟检查属于下一次发布窗口。
